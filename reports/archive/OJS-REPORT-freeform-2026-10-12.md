# Локальная проверка Open Journal Systems

Проверка выполнена 7–12 октября 2026 года. Цель — развернуть OJS и проверить, можно ли провести редакционный процесс Вестника НГУ, ИТ: подачу статьи, слепое рецензирование, доработку, согласование PDF и публикацию. Использовались только тестовые статьи и аккаунты.

Основной процесс удалось пройти без изменения ядра OJS. Статья А опубликована после двух раундов рецензирования, статья Б отклонена, статья В добавлена в уже опубликованный выпуск. При этом обнаружена проблема безопасности: API раскрывает рецензенту имена и почту авторов до публикации. До её исправления считать проверенную сборку пригодной для двойного слепого рецензирования нельзя.

## Как развернули систему

Использовали OJS 3.5.0.5 и готовый образ `pkpofficial/ojs:3_5_0-5`. Стенд собрали через Docker Compose из трёх сервисов:

- OJS с Apache и PHP — само приложение и веб-сервер;
- MariaDB — база пользователей, статей, рецензий и статусов;
- Mailpit — локальный перехватчик писем для проверки уведомлений.

Docker работал через Colima на Mac с ARM64. Для образа OJS указали `platform: linux/amd64`, поэтому приложение запускалось через эмуляцию. Базу и файлы вынесли в постоянные Docker-тома, чтобы они не исчезали при удалении контейнера.

В `compose.yaml` описали сервисы, порты, тома и зависимости запуска. Через `docker/bootstrap.php` подготовили конфигурацию OJS: подключение к базе, локальную почту, адрес сайта и каталог рукописей. В `docker/php.ini` и `docker/apache-local.conf` вынесли дополнительные настройки PHP и Apache. Собственный образ не собирали, код приложения не меняли.

После запуска `docker compose up -d` открыли установщик на `http://localhost:8080`, завершили установку и создали тестовый журнал. Включили русский и английский языки, раздел научных статей, двойное слепое рецензирование и минимум две подтверждённые рецензии. Тексты информационных страниц адаптировали с [действующего сайта журнала](https://intechngu.elpub.ru/jour).

Для полного прогона использовали уже созданный стенд. Предыдущую тестовую статью и выпуск сохранили. Всего подготовили 11 аккаунтов: администратора, главного редактора, редактора, пять рецензентов и трёх авторов. Действия выполняли через кабинеты пользователей, API и штатные обработчики форм OJS; для повторяющихся операций использовали скрипты. Письма проверяли в Mailpit на `http://localhost:8025` — на настоящие адреса они не отправлялись.

## Сложности и возможные решения

**Docker сначала не был запущен.** Клиент выдавал ошибку подключения к Docker daemon. Запустили Colima командой `colima start`, после чего Docker стал доступен.

**Тег образа `stable` отсутствовал.** Запрос к `pkpofficial/ojs:stable` вернул `no such manifest`. Использовали конкретный тег `3_5_0-5`. Для повторяемого развёртывания следует явно фиксировать версию образа.

**Apache не запускался с исходным механизмом блокировок.** Помогла настройка `Mutex fcntl:/var/lock/apache2 default`. Проблема устранена конфигурацией, без изменения OJS. Связь сбоя именно с разницей архитектур не доказана.

**Русский перевод неполон.** На странице пользователей вместо некоторых названий видны ключи `##invitation...##` и `##userAccess...##`; аналогичный пропуск есть в поиске. На английском страница пользователей отображалась корректно. Возможное решение — проверить загрузку переводов для этой версии и дополнить недостающие строки.

**Рецензент получает авторов через API.** В интерфейсе имена скрыты, проверенный DOCX обезличен, приглашение не содержит авторов. Однако до публикации отдельная сессия рецензента получила ФИО и email всех трёх соавторов через `/api/v1/submissions/2/publications/2/contributors`. Это нарушает двойное слепое рецензирование. Нужно исследовать проверку прав этой ручки, исправить выдачу данных и проверить остальные способы получения авторов. Исправление не выполняли; возможность обойтись плагином без изменения ядра не подтверждена. [Сохранённый ответ API](/Users/shemchuk/Projects/vestnik/evidence/full-run/A-reviewer-contributors-current.json) получен до публикации; сейчас А уже опубликована, поэтому повторный запрос к ней не докажет нарушение.

**Два контактных автора не получились.** Трёх соавторов добавить удалось, но `primaryContactId` хранит только одного основного контакта. Рассылка соавторам работает, однако это не заменяет два контактных автора. Если требование сохраняется, нужно уточнить обязанности контактов и расширить форму, хранение и правила рассылки.

**Четыре своих рекомендации не заменили штатный список.** Добавленные варианты видны в пользовательской форме, но рецензент всё равно должен выбрать одну из шести штатных рекомендаций OJS. Возможное решение — согласовать соответствие двух списков или доработать форму так, чтобы не требовать двойного выбора.

**Даты в приглашениях расходятся с формой.** В письме срок оказался на сутки раньше указанного в назначении. Причину не установили. Нужно проверить обработку дат и часовых поясов, затем повторить проверку назначения и письма.

**Часть действий требовала ручного обходного пути.** Возврат оформления и согласие автора на PDF оформлены обсуждениями. Передача v2 в новый раунд выполнена загрузкой тех же байтов после отказа испробованного REST-вызова копирования. Процесс удалось завершить, но для дальнейшей автоматизации нужно отдельно проверить полноту публичного API; некоторые действия сейчас выполнены через внутренние обработчики форм.

**Напоминания потребовали запуска задачи и очереди.** Получение двух писем подтвердили, но постоянное расписание не настраивали. Для самостоятельной работы уведомлений нужен регулярный запуск планировщика и обработчика очереди.

**Загрузка PHP/HTML не была отклонена API.** Инертный PHP-файл сохранился как `.txt`, HTML — как `.html` вне публичного каталога сайта. Исполнение кода не проверяли, поэтому это не доказательство возможности выполнить код на сервере. Перед эксплуатацией нужно определить допустимые типы файлов и проверить ограничения загрузки и выдачи.

**Архив не сразу восстановился между томами.** При распаковке возникла ошибка жёсткой ссылки между томами приложения и рукописей. Исправили создание архива параметром `tar --hard-dereference` и повторили восстановление успешно.

## Дополнительные проверки и результат

Автор А не смог получить чужую статью Б и её файл; неназначенный рецензент также не получил Б. Приватная рукопись не выдавалась без входа, а опубликованный PDF был доступен посетителю. При отказе скачивания OJS иногда возвращает HTTP 200 с `status=false`: для оценки доступа проверяли содержимое ответа, а не только HTTP-код.

Написали небольшой скрипт, который получает статусы статей через API и записывает изменения в лог. Он зафиксировал переход А в Production и затем в Published. Это прототип с опросом API; постоянный сервис не запускали. Также получили XML-ответы OAI-PMH для экспорта метаданных.

Сделали резервную копию: дамп базы данных и архив файлов. Пересоздали основной контейнер с сохранением томов. Отдельно восстановили копию в новые пустые тома и проверили четыре статьи, 11 пользователей и PDF. Временный стенд после проверки удалили. По завершении работы контейнеры основного стенда тоже остановили и удалили; тома с данными и бэкап сохранены.

OJS показала, что требуемый редакционный цикл можно выполнить без изменения ядра, а статьи можно добавлять по одной в уже опубликованный выпуск. Самая существенная найденная проблема — раскрытие авторов через API. До исправления и повторной проверки безопасности выбор этой сборки как основы остаётся открытым. Реальное обновление между версиями с миграцией данных этим прогоном не проверено.
